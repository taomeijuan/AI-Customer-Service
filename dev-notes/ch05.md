## 阶段 0：需求与环境（2026-10-07）

**用户关键原话**：
- 「我要用 Superpowers 模式把客服系统升级成生产级架构：Workflow 确定性编排做骨架，主力 Agent 作为骨架里的核心节点。」
- 要点：①祛魅热身——先不用框架手写最裸的 Agent 循环（调 LLM、有工具就执行喂回、没有就收敛），再用 LangGraph 重构；②图骨架：指代消解（本章透传）→ 意图识别（简单 prompt 七类 JSON）→ 按意图分流 → 知识检索（复用 ch03/04 检索器）→ 置信度闸（复用 ch04 阈值，弱则兜底话术+记录入池不进 Agent）→ 主力 Agent（ReAct：简单一次收敛、复杂多步、缺信息追问，停机条件+token 控制，复用 ch02 工具不新写）→ 日志记录；③分流规则写死代码：知识类（商品咨询、退款退货）强制先检索过闸；业务数据类（物流、订单、售后）直接进 Agent；投诉不进 Agent 只安抚话术+前端自选「转人工」「建工单」（两回事、分开、不自动执行）；闲聊固定话术零模型调用；④State 贯穿 + 自带 checkpointer 持久化；⑤前端：SSE 上加可选按钮渲染，点转人工前端模拟「已转接人工客服」+客服小猫问候，点建工单才写 tickets 表，互不绑定、不点就正常对话
- 技术栈定死：LangGraph（图编排+State+checkpointer）；前端原生 HTML/CSS/JS
- 不做：意图识别/指代消解正式版、上下文管理升级、MCP、飞轮入库
- 验收：①政策问题日志可见强制检索节点 ②「订单 1001 的物流」Agent 自调工具 ③「我要投诉」出两独立按钮、转人工前端模拟、建工单才写表、互不绑定 ④闲聊固定话术 ⑤先查订单再查物流的复杂问题 ReAct 多步可见

**关键产出**：任务跟踪（#27-30）

**用户拒绝或纠偏**：无。

**翻车与返工**：无。
